# Roomies — Rails application

Rails 8.1 · PostgreSQL · Bootstrap 5 (through `cssbundling-rails`).

## Requirements

- Ruby **3.4.5** (see `.ruby-version`; use rbenv, asdf, mise or RubyInstaller)
- PostgreSQL 14 or newer, running locally
- Node.js and Yarn (to build the Bootstrap stylesheet)
- **libvips**, which Active Storage uses to resize listing photographs (`brew install vips` on macOS,
  `sudo apt install libvips` on Ubuntu/WSL)

> **Windows:** we recommend running the project inside WSL 2 (Ubuntu). `bin/dev` relies on `foreman`, which does not run reliably on native Windows.

## Setup

```bash
cd roomies
bundle install
yarn install
```

### Database connection

On macOS with Postgres.app or Homebrew, the default settings work as they are.
If your PostgreSQL needs a host, user or password (Windows, WSL, most Linux installs), export these variables before running any `bin/rails` command:

```bash
export DB_HOST=localhost
export DB_USERNAME=postgres
export DB_PASSWORD=your_password
```

### Create, migrate and seed the database

```bash
bin/rails db:create
bin/rails db:migrate
bin/rails db:seed
```

To start over from an empty database at any time:

```bash
bin/rails db:reset   # drop, create, load schema and seed
```

## Run the application

```bash
bin/dev
```

`bin/dev` starts the Rails server and the Bootstrap/Sass watcher together (see `Procfile.dev`).
Open <http://localhost:3000>.

## Listing photographs

Hosts upload a listing's photographs from the listing form (several at once), and can remove
them when editing it. They are stored with Active Storage; in development, on disk under
`storage/` (see `config/storage.yml`). The Active Storage tables come with the migrations, so
`bin/rails db:migrate` is the only setup step (no `active_storage:install` needed).

- **Upload limit: 10 MB per photograph.** Only JPEG, PNG and WebP images are accepted, and a
  listing has at most 10 photographs. Both rules are validated in the models
  (`ListingPhoto` and `Listing`); the file field's `accept` attribute is only a convenience.
- **Variants:** the listing cards use a 600×400 `:card` variant and the gallery thumbnails a
  400×300 `:thumb` variant, so a card never downloads the full-resolution file. Only the main
  photo of the listing page uses the larger `:large` variant (at most 1600×1200).
- The seed photographs from Assignment 2 still point to external URLs (`image_url`); they are
  shown as they are, while uploaded photographs go through the variants above.

## Rich text (description and house rules)

A listing's description and house rules are written with Action Text: the listing form shows
a Trix editor with bold, italics, lists and links, and the listing page renders the formatted
HTML. The text is stored in `action_text_rich_texts`; the migration
`MoveListingTextsToActionText` copies the plain text of existing listings there (one paragraph
per `<p>`) and removes the old `listings.description` and `listings.house_rules` columns.
Trix's JavaScript is served by the `actiontext` gem through the import map, so there is nothing
to install: `bin/rails db:migrate` is the only step. File attachments are turned off in the
editor because photographs belong in the listing's photo field.

## Business rules and Hotwire

The rules live in the models (`Listing`, `Application`, `Visit`, `Review`); the views only
show the actions each state allows.

- **Listing lifecycle:** a listing is created as a *draft*, visible only to its host. The host
  publishes it, withdraws it (and can publish it again), and marks it as *rented* once the
  housemate has moved in. Accepting an applicant is what moves it to *reserved*. Only
  published listings take applications.
- **Applications:** a seeker can't apply twice to the same listing nor to their own property.
  The author can withdraw it while it is pending or shortlisted. The host shortlists, rejects
  or accepts it from the application inbox (*Applications → Received*) or from its page.
- **Accepting an applicant** (`Application#accept!`): the application is accepted, every
  other pending or shortlisted application to the listing is rejected, and the listing is
  reserved, in a single transaction with row locks, so if any step fails nothing changes.
  A listing has at most one accepted application (validation + partial unique index).
- **Visits:** proposed only on a shortlisted application, never in the past; a proposed visit
  can be confirmed, rescheduled or cancelled, and a confirmed one completed. Only a completed
  visit enables a review.
- **Turbo Frame:** applying from the listing page replaces only the apply block
  (`application_box` frame) with the confirmation and the state of the application.
- **Turbo Stream:** answering from the inbox replaces the affected rows (on accept, also the
  ones rejected automatically), the pending count and the flash without reloading the page.

## Accounts and roles

Accounts use the authentication generated by Rails 8 (`bin/rails generate authentication`):
sessions in the `sessions` table, `has_secure_password`, and password reset by email with a
signed token that expires in 15 minutes. On top of it Roomies adds sign up
(`RegistrationsController`, a new account is always a *member*), the member's own profile at
`/profile` (name, email, phone and a short bio), and Bootstrap versions of every generated view.

- **Visitor** (not signed in): the landing page, the search, the listing and property pages
  with their reviews, and the neighborhoods. Any other page asks to log in first and, after
  logging in, comes back to the page that was asked for.
- **Member** (`role: member`, the default): looks for a room as a seeker and publishes rooms as
  a host. What they can do depends on ownership (see the authorization section).
- **Moderator** (`role: moderator`): everything a member can do, plus resolving reports and
  managing the neighborhood and amenity catalogs.

### Authorization (Pundit)

Every model has a Pundit policy in `app/policies`. The base class is `BasePolicy` and not
Pundit's usual `ApplicationPolicy`, because in Roomies that name belongs to the policy of the
`Application` model (a seeker's application to a room). A **visitor** is not a role: it is a
request with no signed-in user, and every policy answers for `user == nil`.

| Action | Visitor | Member | Moderator |
| --- | --- | --- | --- |
| Browse and search published listings | Yes | Yes | Yes |
| See a draft listing | No | Only their own | Yes |
| Create a property or a listing | No | Yes (rooms only in their own property) | Yes |
| Edit or delete a property or listing | No | Only their own | Any |
| Apply to a listing | No | Yes, except on their own | Same as a member |
| See the applications on a listing | No | On their own listings, plus the ones they wrote | Yes (the *All* tab of the inbox) |
| Shortlist, reject or accept an application | No | Only on their own listings | No |
| Propose or cancel a visit | No | Host of the listing, or the applicant | No |
| Write a review | No | Only after their own completed visit | No |
| Delete a review | No | Only their own | Any |
| Report a listing | No | Yes (not their own) | Yes |
| Resolve a report | No | No | Yes (`/reports`) |
| Manage neighborhoods and amenities | No | No | Yes |

- **Scopes:** the host's inbox and the seeker's list of sent applications are built from
  `ApplicationPolicy::Scope`, so the query only returns what the user may see. Drafts are hidden
  by `ListingPolicy::Scope` on the search and the property pages.
- **Enforced in the controller:** hiding a button is only a courtesy. Every action calls
  `authorize`, and `after_action :verify_authorized` fails if one forgets to. Typing the id of
  someone else's application, or sending a `PATCH` by hand, is refused.
- **The 403 page:** an unauthorized attempt renders `app/views/errors/forbidden.html.erb` with
  status 403 and an explanation of the rule that blocked it (`config/locales/en.yml`, keys
  `pundit.<policy>.<action>`), never a raw error.

### Notification emails (Active Job)

Roomies emails each side of an application when something happens to it
(`NotificationsMailer`):

- **New application → the host:** who applied, to which room, the move-in date, the length of
  the stay and the message, with a link to answer it.
- **Answer → the seeker:** when the host shortlists, accepts or rejects the application.
  Accepting one also emails every seeker whose application was rejected automatically.

They are sent with `deliver_later`, so Active Job delivers them in the background and the page
doesn't wait for the email (the `:async` adapter in development, Solid Queue in production).
Their design can be previewed at <http://localhost:3000/rails/mailers/notifications_mailer>.

### Emails in development

In development no email leaves your computer: they are delivered by `letter_opener_web` and
listed at <http://localhost:3000/letter_opener>. To try the password reset, choose *Forgot your
password?* on the log in page, then open the email there and follow its link. To see a
notification, apply to a room as a seeker, or answer an application as its host. Emails are sent in
the background with Active Job (`deliver_later`).

## Public JSON API (v1)

A read-only API for the published listings, under `/api/v1`. It needs no account and exposes no
personal data: no host or seeker names, emails or phones, no applications, and not the street
address of the property (the host may live there), only its neighborhood. Responses are JSON
with a `data` key; lists also have `meta` (pagination and applied filters) and `links`.

| Method and path | Description |
| --- | --- |
| `GET /api/v1/listings` | Published listings, filtered and paginated |
| `GET /api/v1/listings/:id` | One published listing, with its full description and photos |
| `GET /api/v1/neighborhoods` | The neighborhoods, with how many published listings each one has |
| `GET /api/v1/amenities` | The amenities and shared spaces (to filter by `amenity_id`) |

Query parameters of `GET /api/v1/listings` (all optional and combinable):

| Parameter | Example | Meaning |
| --- | --- | --- |
| `neighborhood_id` | `3` | Only rooms in that neighborhood |
| `amenity_id` | `5` | Only rooms whose property has that amenity |
| `max_rent` | `400000` | Monthly rent up to this amount (CLP) |
| `available_by` | `2026-12-01` | Rooms you can move into by that date (`YYYY-MM-DD`) |
| `sort` | `rent_asc` | `newest` (default), `rent_asc` or `rent_desc` |
| `page`, `per_page` | `2`, `12` | Pagination: pages start at 1; `per_page` from 1 to 50 (default 12) |

Status codes:

| Status | When |
| --- | --- |
| `200 OK` | The listings (possibly an empty `data` array) or the listing |
| `400 Bad Request` | A malformed parameter; `error.details` names each one and what is wrong |
| `404 Not Found` | The listing doesn't exist or isn't published (drafts are never exposed) |

```bash
curl "http://localhost:3000/api/v1/listings?max_rent=400000&sort=rent_asc&per_page=2"
```

### The search page uses the API

`/listings` is rendered by the server the first time (so it works without JavaScript and keeps
the Assignment 3 search). Then the Stimulus controller `listing_search_controller.js` takes over:
changing a filter or submitting the form calls `GET /api/v1/listings` with `fetch`, draws the
cards from the JSON, shows a *Show more rooms* button while there are more pages, reports a 400
in an alert, and keeps the address bar in sync with the filters.
